---
title: 'Tenants: store host -> Auth0 organization'
description: 'How the store surface resolves its tenant from the request host.'
---

The store surface resolves its tenant from the request host (`x-merkaly-host`, see
`RouterMiddleware`): `StoreGuard` and `GET /store/tenant` call `ResolveService`, which reads the
in-memory map of `TenantService`. No request asks Auth0 once the map is loaded.

Business side (organization, store subdomain, discovery domains, the Auth0 event flow):
[docs.merkaly.io/identidad](https://docs.merkaly.io/identidad).

## Pieces

| Piece | File | Role |
| --- | --- | --- |
| `TenantService` | `src/infrastructure/services/tenant.service.ts` | Builds and holds the map, exported by `AppModule` |
| `ResolveService` | `src/application/store/resolve/resolve.service.ts` | Host -> tenant for the store, fallback while the map is not loaded |
| `AccountOrganizationListener` | `src/domain/account/listeners/organization.listener.ts` | Applies the Auth0 organization events |
| `store.domain.ts` | `src/infrastructure/utils/store.domain.ts` | `normalizeHost`, `isBareStoreHost`, `storeNameOf`, `storeDomain`, `isInternalStoreDomain` |

A `Tenant` is `{ id, name, displayName, sellerId, domains, logoUrl, primaryColor }`: the Auth0
organization id and name, `display_name`, `metadata.aliexpressSellerId`, its discovery domains
(lowercase) and `branding.logo_url` / `branding.colors.primary` (read for the store identity copy,
see the account README). Queries:
`byHost`, `byId`, `byName`, `bySeller`, `list`.

## Lookup (`byHost`)

1. The host is normalized (lowercase, no port, no trailing dot) and validated as a hostname
   (RFC 1123 labels, at least one dot, 253 chars max). Invalid: `null`.
2. Bare store hosts (`merkaly.store`, `store.merkaly.test`): `null` (`StoreGuard` handles the dev
   store with `identity`).
3. A discovery domain of some organization wins; otherwise `<name>.merkaly.store` (first label,
   every env) by organization name.
4. Anything else is `null`, so the store answers `404` without calling Auth0: an unknown host
   (`x-merkaly-host: random.com`) costs nothing. This is the negative cache.

## Loading

- On boot (`onApplicationBootstrap`, never blocks it): outside production from
  `.cache/auth0.organizations.json` (gitignored); otherwise, or with a missing or invalid file, from Auth0:
  `organizations.list` (100 per page) plus `discoveryDomains.list` per organization, 5 in flight.
  Production (Railway, ephemeral disk) keeps the map in memory only. An empty map is never written.
- A boot load from the file is only a fast start: right after applying it, a **full reload from
  Auth0** runs in the background (`refreshAfterFile`). A local api misses the organization events
  while stopped, and the queue is shared with production (each event goes to one consumer), so the
  file can hold deleted or changed organizations. A failed reload keeps the file map and retries
  with the same backoff.
- A failed load logs an error and retries with exponential backoff (5 s up to 15 min).
- There is **no periodic reload**: after the boot load only the organization events and the api's
  own changes update the map. Accepted risk: an event taken by another consumer of the shared queue
  (e.g. a local api) is only corrected on the next deploy or restart (until the queues get one
  vhost per environment and the caches move to Redis).
- Outside production every change is written back to the file (writes in order).

### Before the first load

`ResolveService` falls back so the stores keep working: `<name>.merkaly.store` costs one
`organizations.getByName` (as before this cache), custom domains answer `503` (the full Auth0 scan
is gone for good), bare hosts `null`.

### After a full load

Every full load from Auth0 (not from the file) emits `TENANTS_LOADED` (in process, data = the
tenants read). `AccountOrganizationListener` runs `AccountOrganizationSyncFlow.syncOrganizations`
with them, per organization: the store identity copy in Mongo (only on diff) and the internal
store domain healing (one Auth0 list and get only when a stale internal domain shows up). The infrastructure
never imports the domain, hence the event. Every api process runs it, the local one too (it shares
the production Mongo and Auth0): idempotent, nothing written when equal.

## Updates

| Trigger | Effect |
| --- | --- |
| `broker.identity.organization.created` | `AccountOrganizationSyncFlow.syncOrganization(id)`: `reload(id)` re-reads the organization and its domains (resolves the tenant read, or `null`), then the store identity copy and the internal domain healing with what it read |
| `broker.identity.organization.updated` | same, also picks up domains changed meanwhile |
| `broker.identity.organization.deleted` | `remove(id)` |
| `AccountStoreProvisionFlow` (`POST /www/onboarding` and the signup Action) | `reload(id)` after the member step, so the new store resolves right away |
| `AccountStoreRenameFlow` (`PATCH /admin/settings/organization/store`) | `reload(id)` after the Auth0 rename and the discovery domain swap (old internal domains removed, so their names are free again): the new `<name>.merkaly.store` resolves and the old one answers `404` right away |
| Boot from the file (outside production) | Full reload right away: events missed while the api was stopped or taken by another consumer |
| `GET /store/company` of a store whose Auth0 organization answers `404` (stale map or file, e.g. a deleted org kept by the local cache) | `remove(id)` and `404 Store not found`: the next request asks Auth0 and answers `404` too |
| Restart or deploy | Everything else: events lost to another consumer of the shared queue |

`reload` never rejects: a `404` drops the tenant, other errors log a warn and wait for the next
event or restart. Events are triggers: the data is read from Auth0, not from the payload.

The events come from Auth0 Event Streams through webhooks.merkaly.io (`organization.created`,
`organization.updated`, `organization.deleted` published as `identity.organization.*`, data =
Auth0 `data.object` as is). The Event Stream of the tenant must be subscribed to those three types.

Auth0 Event Streams has **no event for discovery domains** (the catalog has `organization.*`,
`organization.member.*`, `organization.connection.*`, `organization.group.role.*`, `group.*` and
`user.*`). Business rule: store domains change **only through Merkaly** (`Auth0Service.ensureStoreDomain`
and the store rename, each followed by `reload`), never by hand in the Auth0 dashboard. A manual
change is seen only on the next organization event or restart.

## Limits

- The map lives in each process. The Rabbit queue `api.merkaly.io` delivers each event to **one**
  consumer: with several api replicas only one would apply it and the others would wait for a
  restart. Today there is one replica; scaling out needs a fanout (one queue per replica) or
  a shared store.
- The boot load costs `1 + organizations / 100` list calls plus one discovery domain call per
  organization. Fine for hundreds of stores; at a larger scale move the map to a Mongo collection
  kept by the same events.
- Other readers of the full organization list still call Auth0 and can move to `TenantService`:
  `DashboardPaymentService.stores()` (`list()`), `DashboardClientsController.list()` (needs
  `metadata.email`, not kept today) and `SupplierAliexpressSellerService` (`bySeller()`).
