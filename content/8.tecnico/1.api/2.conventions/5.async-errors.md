---
title: 'Async errors convention: promise chaining over try/catch'
description: 'Promise chaining over try/catch for asynchronous code.'
---

> **Rule:** handle errors of asynchronous code by **chaining** `.then()` / `.catch()` /
> `.finally()` on the promise. Do not wrap an `await` in a `try { ... } catch { ... }` block.
> `try/catch` is reserved for **synchronous** code that throws.
> Even then, prefer an API that does not throw: `parseJson()` (`src/infrastructure/utils/json.ts`,
> `undefined` when the text is not JSON) instead of `JSON.parse` in a `try`, and `URL.parse()`
> (`null` when invalid) instead of `new URL()` in a `try`.

## Why

A chain reads top to bottom as the flow itself (call, recover, clean up) and keeps the
fallback next to the call it belongs to. `try/catch` around `await` adds nesting, forces
`let` variables declared outside the block, and makes it easy to catch more than intended
(code added to the block later is silently covered by the same fallback).

## Do

```ts
// Fallback for a failed call, with the long handler extracted to a small private method.
return orders.create({ body, requestOptions }).catch((error) => this.recoverFailedOrder(error, body));

// Best effort lookup: any failure becomes `null`.
return this.$auth0.users
  .get(userId)
  .then((user) => user?.created_at ?? null)
  .catch(() => null);

// Ignore an expected error and always release the resource.
return session
  .withTransaction(async () => {
    await this.$confirm.confirmSalePayment({ method, sale: { _id: sale._id } });
  })
  .catch((error) => {
    if (!(error instanceof ConflictException)) throw error;
  })
  .finally(() => this.$mongo.endSession());

// Recover only the request, not what runs after it: two-argument `then`.
return this.requestToken(request).then(
  (token) => this.saveConnection(token),
  (error) => this.recoverFailedRefresh(error),
);
```

## Don't

```ts
try {
  return await provider.createOrder(body);
} catch (error) {
  if (error instanceof ProviderValidationError) {
    // ...
  }
  throw providerOrderException(error);
}

let token: OAuthResponse;
try {
  token = await request();
} catch (error) {
  throw providerSdkException(error);
}
```

## Keeping behaviour when converting

- **Scope of the catch.** `.catch()` at the end of a chain covers every step before it. When
  the original `try` covered only the call, put the `.catch()` right after it, or use
  `.then(onFulfilled, onRejected)` so the success path is not recovered.
- **Synchronous throws.** A function that may throw before returning its promise (a callback
  parameter, a constructor) is not covered by `.catch()`. Start the chain with
  `Promise.resolve().then(fn)` to turn that throw into a rejection.
- **Long handlers.** When a `.catch()` handler grows past a few lines, extract it to a private
  method (`recoverFailedOrder`, `recoverFailedCancel`, ...).
- **`await` is fine.** `await promise.catch(...)` inside an `async` function is chaining; only
  the `try` block around it is avoided.

## Allowed exceptions (try/catch stays)

- **Synchronous code that throws**, with no promise to chain: `JSON.parse`, `Buffer.from`,
  `new URL(...)`, crypto helpers. Leave a one-line `//` comment saying why.
- **Cases where a chain is clearly more confusing**, e.g. a loop with `break`/`continue`
  depending on each awaited result. Document the reason inline.
