The business side of each domain (what it is, entity map, lifecycles, animated flows and decisions)
is on [docs.merkaly.io](https://docs.merkaly.io): Identidad, Tienda, Catálogo, Pedidos, Pagos, Proveedores and Plataforma.
This file keeps the code boundaries.

The approved roots are Account, Assets, Catalog, Order, Finance, Logistics, Payment, Provider and
Settings. There is no `integration` root: integrations (optional things the merchant connects, such as
pixels, webhooks or an own domain) are not implemented yet. See the decision
[El proveedor no es una integración](/proveedores/decisiones/proveedor-no-es-integracion). Nest modules wire dependencies; application surfaces expose use cases.
A business boundary does not require an empty Nest module.

| Root | Current responsibility | Implementation status |
| --- | --- | --- |
| Account | User identity, saved addresses and payment methods | Existing implementation retained |
| Assets | Media and asset references | Existing implementation retained |
| Catalog | Products, variants, categories and brands | Moved from inventory; no own stock model |
| Order | Buyer sales and merchant procurement | Existing sale/purchase behavior retained; connected-provider flow pending |
| Finance | Merchant payment records | Existing safeguards retained; no new Merkaly billing |
| Logistics | Shipments and their tracking timeline (returns, carriers later) | See order-lifecycle.md |
| Payment | Store payment accounts (one per gateway, `payment.accounts`) and the bridge to payments.merkaly.io | `src/domain/payment` |
| Provider | Dropshipping sources (AliExpress today): the account Merkaly operates per organization (`providers`), import, sync, quotes and orders | `src/domain/provider` |
| Settings | Tenant-local store configuration by key (`organization` values, `payment`: primary gateway, fallback, methods); values only, never secrets | `src/domain/settings` |

Catalog owns merchant-facing descriptions and retail prices. Provider owns the provider account and
access, not Catalog; Order coordinates procurement; Finance keeps the financial records.

Provider: `src/domain/provider` keeps one document per provider in each organization database
(`providers`, unique index on `provider`) with the account Merkaly operates in `account` (login,
seller id, tokens and their expiry). The per-provider adapters live in `src/domain/provider/<provider>`
(`aliexpress/` today). The merchant admin only imports and syncs products
(`/admin/providers/aliexpress/...`); the connection is a Merkaly staff operation of the dashboard
(`/dashboard/clients/:client/providers/aliexpress/connection`). See `src/domain/provider/README.md`.

Payment: `src/domain/payment` owns the store payment accounts and asks the gateway only through
payments.merkaly.io (stateless, RabbitMQ invokes, `PaymentGatewayService`). Every record (payments,
refunds, withdrawals, chargebacks, debts) and every rule stay in the api; payments answers in Merkaly
terms (cents, coarse statuses) and the api never decides with a raw gateway status. The gateway the
store uses is the `primary` of the `payment` settings key (default ASAAS). See
`src/domain/payment/README.md`.

## Compatibility during naming transition

Source imports now use `src/domain/catalog`. Retained catalog HTTP routes, exports and Mongo names stay compatible. Measurement/configuration endpoints, exports and Product.measure are deliberately removed from this phase. This avoids a database migration or consumer rollout for a source-only
reorganization. The contracts manifest must map those public exports to the new
source paths before its next synchronization.

Application folders retain their current surface-oriented layout. Internal
resource modules remain where they provide actual dependency wiring. InventoryModule was removed with the old inventory root. OrderModule remains an
optional grouping module importing and exporting SaleModule and PurchaseModule;
consuming surfaces continue to import their functional modules directly.

No stock, fee, provider integration, payment confirmation, deployment or data reset
is introduced by this change.

## Measurement removed from the initial phase

Founder explicitly removed measurement/unit functionality: catalog configuration,
CRUD endpoints, Mongo registration, product measure field and virtual, validators,
generated contracts, Admin selector/adapters and Store display/joins. No database
drop or migration runs; existing test documents are not rewritten. Future provider
dimensions are undefined and must not be inferred from this removal. Coordinate
API #1314, contracts #39, Admin #824 and Store #479; publish/deploy separately.

## Additional initial-phase reductions

Collections and local attribute definitions are removed, including product
attributes and the dependent local variant options schema/comparison helpers.
The legacy VariantIdentifierEntity (sku/gtin) and its synchronization are removed.
Product.sku and its existing index remain an independent internal product code,
not a provider external variant ID. Variants, their technical IDs and product
relation remain. Provider options/IDs and functional SKU selection are future
work, not implemented replacements. No database drop or index migration runs.

## Invoice and Refund deferred

The initial phase excludes Finance Invoice and Refund resources, CRUD, contracts,
Mongo registration and sequence definitions. Payment remains unchanged, including
historical REFUNDED values with no enabled confirmation path. Canceling an order
does not prove a refund. Refund and Disputes are future capabilities, with no
scaffolding or payment-evidence mechanism implied. No fiscal invoicing is delivered.

Admin navigation still links to /finance/invoices and /finance/refunds pending
frontend cleanup. No database drop/index migration or frontend change is
included.

## Canonical catalog prices

Product persists sellPrice and buyPrice directly, without price/cost aliases.
Variant.sellPrice retains the previous supplemental amount added to product
sellPrice; it is not a new absolute provider price. Historical order item.price
snapshots remain unchanged. Store responses omit buyPrice and legacy cost,
including populated products.

This changes existing Mongo keys: old price/cost product records and price variant
records require a separately authorized migration before release. No migration,
reset, fallback aliases or data rewrite is included. New catalog documents use
the canonical keys. No package publication or deployment is included.
