---
title: 'Layers and file roles'
description: 'Orchestrated flows and the one job of each file role.'
---

Business flows are **orchestrated, never choreographed**: one flow method reads top to bottom, calls
each step, waits, looks at the result and decides. No business step is triggered by an event or a
hook. Each file type has one job:

| Layer | File | Does | Never |
|---|---|---|---|
| Entry | `.controller` | Validates the request, calls **one** flow (or one service for plain reads and CRUD) | Business rules, repositories, sessions or transactions |
| Entry | `.listener` | Receives a broker event, translates its payload, calls **one** flow | Business rules, repository writes |
| Entry | `.responder` | Answers a broker invoke (`@HandleInvoke`, request-reply), calls one flow | Writes beyond what the flow does |
| Entry | `.command` | Console entry (`pnpm console`), calls flows or services | Business rules |
| Entry | `.guard`, `.strategy`, `.middleware` | Authentication and access, before the controller | Business rules |
| Orchestration | `.flow` | One business flow: loads, validates, calls services in order, opens the transaction, makes the external calls before or after it, recomputes derived state, returns | Raw queries, provider HTTP |
| Domain | `.service` | One capability of its domain: the rules of its entities, through its repository | Writing through another domain's service or repository, emitting events to trigger steps |
| Domain | `.transition` | Allowed status moves of an entity | Side effects |
| Domain | `.enum`, `.types` | Closed values; types and constants | Logic |
| Domain | `.exception` | Own errors | |
| Data | `.entity` | Document shape (`@Prop`) and virtuals | Rules |
| Data | `.schema` | Mongo registration: indexes, plugins, query hooks | Rules |
| Data | `.repository` | Reads and writes **one** collection (or one settings key) with explicitly named methods | Business rules, HTTP exceptions |
| Data | `.pipeline`, `.stages` | Aggregations, run only from their repository | Business values (they come as parameters) |
| Data | `.plugin`, `.seeder` | Generic schema behavior; test data | |
| External | `.client` | HTTP with a provider or gateway (transport only) | Rules, persistence |
| External | `.adapter` | Translates provider calls and answers to Merkaly terms | Business rules, persistence |
| External | `.mapper` | Pure translation functions (statuses, money, payloads) | I/O |
| Cross-cutting | `.module`, `.validator`, `.decorator`, `.filter`, `.interceptor`, `.pipe`, `.router` | Nest wiring and request/response plumbing | Business rules |
| Cross-cutting | `utils/` | Pure helpers without business meaning | Business rules (they belong to a service or a flow) |

## Flows

How a flow is written inside (`execute(request)` as its only public method, `assert*` / `resolve*` /
`apply*` helpers, `afterCommit`) is in [Flows: execute y helpers](/tecnico/api/conventions/flows).

```ts
// src/domain/catalog/flows/product.delete.flow.ts
@Injectable()
export class CatalogProductDeleteFlow extends AbstractFlow<CatalogProductDeleteRequest> {
  @Transactional()
  public async execute(request: CatalogProductDeleteRequest): Promise<void> {
    const productId = await this.resolveLockedProductId(request.product); // load and lock
    await this.assertProductHasNoOrders(productId);                       // the decision
    await this.$products.deleteLockedProduct(productId);                  // the write
  }
}
```

- **Where:** `src/domain/<owning domain>/flows/<entity>.<action>.flow.ts`, class
  `<Domain><Entity><Action>Flow`, one public method `execute(request)` with a named request type
  (`<Domain><Entity><Action>Request`).
- **Order:** load and validate, external reads, one transaction for the writes, external writes after
  the commit. Writes that the provider must find before answering (e.g. the refund record the provider
  refund check looks up) go in a short transaction before the external call.
- **External calls never run inside a transaction** (payments.merkaly.io invokes, AliExpress, Auth0, storage).
- **Derived state is recomputed explicitly** (`OrderSaleStatusService.recompute`) by the flow that
  changed its inputs, inside its transaction.
- **A flow may call another flow** when the business says so (a supplier cancellation cancels the
  sale): it injects it and calls its `execute`, still explicit and in order.
- **Events** only carry what is really asynchronous: broker events in (each listener calls one flow)
  and notifications out (the store SSE `OrderSalePaymentEvent.CHANGED`). There are no `@Hook`s.
- **Every flow extends `AbstractFlow`** (`src/infrastructure/abstracts/abstract.flow.ts`): it brings
  `$cls` and `$logger`, plus `runAsSystem(work)` (same organization, no session nor user: written by
  the system, `null` author), `runInBackground(work, failure)` (as the system, not awaited, a
  failure is logged) and `afterCommit(work)` (after the surrounding transaction commits). The services a flow calls stay injected in the flow itself, never resolved
  with `ModuleRef`: its dependencies read at the top and a missing one fails at boot.
- A flow is a provider of its domain module, which imports the modules of the services it calls.

## Repositories

- Every repository extends `AbstractRepository` (`src/infrastructure/abstracts/abstract.repository.ts`).
- Public: `read`, `search`, `count`, `create`, `update`, `delete`, `aggregate` (until the pipelines
  move to their repositories).
- Protected building blocks for named methods: `find`, `findOne`, `exists`, `updateOne`
  (`{ upsert }`), `updateMany` and `bulk` (one `bulkWrite`). All of them add `deletedAt: null`
  (except `bulk`, whose operations carry their own filter).
- Reads come in two shapes:
  - `find` / `findOne`: plain objects (`lean`), to read and decide (ids, statuses, totals). Faster and
    lighter, but no virtuals (`number`, `id`), getters, defaults or `save()`.
  - `findDocuments` / `findOneDocument`: Mongoose documents, when the result is answered to the client
    (`toJSON` adds `id`, `number`, getters), a virtual is read, or the document is saved.
  - Both take `select`, `sort`, `join` (and `limit` for lists). `read` and `search` keep returning
    documents.
  - `skipDefaults: true` (also on `read`, and as `options: { skipDefaults: true }` inside a `join`
    entry) skips the default populate of the schema query hooks (catalog product, category and brand).
    Only for reads that use ids or raw fields and never answer the entity to a client.
- Method names say what they do and to what: `getOpenDebts`, `settleDebtsByWithdrawal`,
  never `open()`, `record()` or `settle()`.
- The service passes the business values (statuses, dates, limits) as parameters; the repository
  only turns them into a query.
- Pipelines live in `<domain>/pipelines/*.pipeline.ts` and run from a named repository method.

```ts
// No (service)
await this.$debts.$builder.find({ status: 'OPEN' }).sort({ createdAt: 1 }).lean().exec();

// Yes (repository + service)
public getOpenDebts() {
  return this.find({ status: FinanceDebtStatusEnum.OPEN }, { sort: { createdAt: 1 } });
}
const debts = await this.$debts.getOpenDebts();
```

Approved exceptions to `$builder` outside a repository are listed in `eslint.config.mjs` with their
reason (today only the seeders: test data written straight to the collections). A one-off case
carries it on the disable comment: `// eslint-disable-next-line no-restricted-syntax -- approved: <reason>`.

## Errors

Repositories throw `RepositoryException`s (`src/infrastructure/exceptions/repository/`), never
HTTP exceptions:

- `DuplicateRecordException`: a unique index refused the write (409). Carries `field` and `value`.
- `InvalidJoinException`: a `join` path the schema does not have (422).

`RepositoryFilter` answers them with the real message and `params`
(`{ error, message, params, statusCode }`). A service that expects one catches it by class:
`error instanceof DuplicateRecordException && error.field === 'slug'`. `EntityNotFoundException`
(404) and `GoneException` (410) stay as they are.

## Transactions

The service method that needs one is marked with `@Transactional()`
(`src/infrastructure/decorators/transactional.decorator.ts`):

```ts
@Transactional()
public async cancel(locator: SequenceFilter) { ... }
```

- It opens the transaction, or joins the one already running (a transactional service calling
  another).
- The session lives in CLS and the global `sessionPlugin` (`src/infrastructure/plugins/session.plugin.ts`)
  adds it to every query, aggregation and save. Nobody calls `.session()` or passes a session, and
  controllers never open one. Only `bulkWrite` (no Mongoose middleware) takes it explicitly, inside
  `AbstractRepository.bulk()`.
- Operations inside a transaction run one at a time (no `Promise.all` over the same session).

## Listeners

A `@Listen` (`<domain>/listeners/*.listener.ts`) runs after the commit in a fresh context (same
organization, no session nor user); broker events reach it as `broker.<type>`. It translates the
payload and calls one flow; a failure is logged (broker events: rejected to the broker for a retry).

## Service contracts

A service method declares what it needs as a named type (`<Domain><Action>Request`), at most two
parameters (three when the last is options). Callers build that type; the service never adapts to a
caller.
