## En un minuto

Los servicios de Merkaly no se llaman entre sí por HTTP: se dejan mensajes en RabbitMQ (el broker). Tres piezas alcanzan para entenderlo:

- Un [exchange](/glosario/exchange) es el buzón de un servicio: `merkaly.api`, `merkaly.payments`. No guarda nada, solo reparte.
- Una [cola](/glosario/queue) es donde un mensaje espera a quien lo va a procesar: `merkaly.api-payments`. Es del que consume.
- La [routing key](/glosario/routing-key) es la etiqueta del mensaje y siempre es su nombre: `payment.received`. Cada cola le dice al exchange qué claves quiere recibir (un binding por clave exacta, sin comodines).

Cuando alguien publica `payment.received` en `merkaly.payments`, el exchange copia el mensaje a cada cola ligada a esa clave. Si no hay ninguna, el publish falla ([mandatory](/glosario/mandatory)): nada se pierde en silencio.

Todo esto lo implementa el paquete [@merkaly/nest](/tecnico/nest/events): los nombres, los reintentos y la forma de cada mensaje ([sobre](/glosario/envelope)) son iguales en todos los servicios.

- **Ruteo explícito**: el mapa proveedor a dueño vive en un solo archivo de webhooks (`src/app.routes.ts`). Cambiar de dueño es cambiar una línea; no hay bindings entre exchanges que escondan el ruteo en el broker.
- **Nombres**: sin prefijo de transporte ni de servicio. Eventos en pasado (`payment.confirmed`), comandos e invokes con verbo (`email.send`, `order.purchase.place`, `payment.withdrawal.authorize`).
- **Ligar desde otro dominio**: una cola puede escuchar el exchange de otro dueño (`from`). El api liga `merkaly.api-payments` a `merkaly.payments` con `from: "payments"`.
- **Orden no garantizado y mensajes repetidos**: un mensaje puede llegar dos veces o fuera de orden. Por eso los eventos solo disparan: el que consume relee el estado real (el api relee el cobro con [payment.charge.read](/glosario/payment-charge-read) y el pedido con `ds.order.get`) y cada handler puede correr dos veces sin efecto doble. Hoy ningún servicio guarda una bandeja de mensajes procesados (el paquete la permite, `inbox`, pero nadie la usa).

## Cuatro formas de publicar

| Forma | Quién publica | En qué exchange | Respuesta | Ejemplo |
| --- | --- | --- | --- | --- |
| [emit](/glosario/emit) (evento) | quien vivió el hecho | el propio | no | payments emite `payment.received`; el api emite `order.sale.paid` |
| [deliver](/glosario/deliver) (evento de afuera) | la puerta, webhooks | el del dueño | no | `supplier.order.status_changed` en `merkaly.api` |
| [command](/glosario/command) (orden) | quien pide algo | el del destino | no | el api se manda `order.purchase.place`; `email.send` para signals |
| [invoke](/glosario/invoke) (pregunta) | quien pregunta | el del que responde | sí, por `amq.rabbitmq.reply-to` | el api invoca `payment.charge.create` |

Eventos y comandos viajan igual: quedan en una cola durable, se confirman (`ack`) cuando el handler terminó y, si fallan, se reintentan por la `.retry` y terminan en la `.dlq` (ver [Reintentos](/plataforma/reintentos)). Un invoke es distinto: es una pregunta con tiempo límite, sin `.retry` ni `.dlq`.

## Exchanges

| Exchange | Dueño | Quién publica ahí |
| --- | --- | --- |
| [`merkaly.api`](/glosario/merkaly-api) | api | el api (sus eventos y comandos), webhooks (AliExpress) y payments (invokes al api) |
| [`merkaly.payments`](/glosario/merkaly-payments) | payments | payments (eventos `payment.*`), webhooks (Asaas) y el api (invokes a payments) |
| [`merkaly.auth`](/glosario/merkaly-auth) | Auth0, vía webhooks | solo webhooks; no hay servicio auth que consuma, lo escucha el api |
| [`merkaly.signals`](/glosario/merkaly-signals) | signals | el api (`email.send`, pedido recibido al comprador) |

## Colas, quién consume y qué mensajes

| Cola | Consume | Ligada a | Mensajes | Quién los pone |
| --- | --- | --- | --- | --- |
| [`merkaly.payments-asaas`](/glosario/merkaly-payments-asaas) | payments | `merkaly.payments` | `payment.asaas.webhook.received` | webhooks |
| [`merkaly.payments-invokes`](/glosario/merkaly-payments-invokes) | payments | `merkaly.payments` | `payment.charge.*`, `payment.account.*`, `payment.transfer.*`, `payment.balance.read`, `payment.fees.read`, `payment.movement.check` | api y webhooks |
| [`merkaly.api-payments`](/glosario/merkaly-api-payments) | api | `merkaly.payments` | `payment.confirmed`, `payment.received`, `payment.refunded` y el resto de `payment.*` de cobros, cuenta y transferencias | payments (traducidos) |
| [`merkaly.api-identity`](/glosario/merkaly-api-identity) | api | `merkaly.auth` y `merkaly.api` | `identity.signup.requested`, `identity.organization.*`; `account.user.linked` | webhooks (Auth0); el propio api |
| [`merkaly.api-supplier`](/glosario/merkaly-api-supplier) | api | `merkaly.api` | `supplier.order.status_changed`, `supplier.product.updated` | webhooks (AliExpress) |
| [`merkaly.api-procurement`](/glosario/merkaly-api-procurement) | api | `merkaly.api` | [`order.sale.paid`](/glosario/order-sale-paid), [`order.purchase.place`](/glosario/order-purchase-place) | el propio api |
| [`merkaly.api-invokes`](/glosario/merkaly-api-invokes) | api | `merkaly.api` | `payment.withdrawal.authorize`, `payment.refund.authorize` | payments |
| [`merkaly.signals-emails`](/glosario/merkaly-signals-emails) | signals | `merkaly.signals` | `email.send` | el api |

Cada cola de trabajo tiene además su `<cola>.retry` y su `<cola>.dlq`. Las colas `-invokes` no.

Los eventos internos del api (por ejemplo `order.sale.payment.changed`) siguen en memoria, no pasan por Rabbit. Lo que llega del broker se reemite adentro con el prefijo `broker.` (`broker.payment.received`) para que nunca choque con un evento interno.

## Limitación actual: una cola, varios api

Hay **una sola cola por trabajo en el broker**, no una por entorno. El api local de desarrollo usa el mismo broker (y la misma base) que producción, así que si se levanta con el mismo `RABBITMQ_URL` se conecta a las mismas colas. RabbitMQ reparte los mensajes entre los consumidores de una cola por turnos: cada mensaje lo procesa solo uno de los dos, y producción nunca ve los que tomó el local.

- Pasa con todas las colas: `merkaly.api-payments`, `-supplier`, `-identity`, `-procurement` y `-invokes`.
- Lo que toma el api local lo procesa el código de su rama, contra la base de producción. Si falla, la `.retry` y la `.dlq` también son las de producción.
- Lo mismo pasa con varias réplicas del api: se reparten los mensajes. Eso está bien mientras corran el mismo código; el problema es mezclar entornos.
- Hoy se evita no consumiendo desde un api local conectado al broker de producción. La solución (colas por entorno u otra forma de consumir) está pendiente.
