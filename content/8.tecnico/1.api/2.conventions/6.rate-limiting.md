Routes that anyone can hit (public forms, payment attempts) get a per-IP request limit with
[`@nestjs/throttler`](https://docs.nestjs.com/security/rate-limiting). Over the limit the api answers
`429 Too Many Requests` and the handler never runs.

## How it is wired

- `ThrottlerModule.forRoot([{ limit: 10, ttl: 60_000 }])` is registered **once**, in `AppModule`.
  It is only the mechanism (storage + defaults). It limits nothing on its own: there is no global
  `APP_GUARD` for it.
- A route opts in with `@UseGuards(ThrottlerGuard)` and **declares its own limit** with `@Throttle`:

```ts
import { Throttle, ThrottlerGuard } from '@nestjs/throttler';

@UseGuards(ThrottlerGuard)
@Throttle({ default: { limit: 5, ttl: 600_000 } }) // 5 per 10 min per req.ip
@Post('/')
public create(@Body() payload: SomeRequestValidator) { ... }
```

- Counters are kept **per route** (the throttler keys them by controller + handler + client), so
  two routes with limits never share a counter.
- Same rule as the query validators: `AppModule` owns the mechanism, each application declares its
  numbers next to the route. No custom guard classes.

## Current limits

| `PUT /auth/me/avatar` | `application/auth` (`/auth`, every app) | 10 per minute per IP | every upload writes to the Auth0 Management API |
| `POST /auth/me/email-verifications` | `application/auth` (`/auth`, every app) | 3 per hour per IP | every call sends an email through Auth0 |

| `POST /admin/settings/organization/branding` | `application/admin` | 10 per minute per IP | up to 3 storage writes (R2) per request |

| `DELETE /admin/settings/team/invitations/:id` | `application/admin` | 20 per minute per IP | Auth0 Management API write |

| `POST /www/onboarding` | `application/www` | 5 per 10 minutes per IP | every call writes to the Auth0 Management API (organization, member, role) |

Update this table when you add or change a limit.

## Client IP (`trust proxy`)

The throttler tracks `req.ip`. `main.ts` sets `app.set('trust proxy', true)`, so Express derives
`req.ip` (and Nest's `@Ip()` decorator) from the **first** `X-Forwarded-For` entry instead of the
socket, which in production is a proxy:

- browser → Cloudflare → Railway → api
- browser → Cloudflare → store (Nuxt server proxy, keeps the original `X-Forwarded-For`) → api

Use `@Ip()` when a handler needs the client IP. Never
read `X-Forwarded-For` or `cf-connecting-ip` by hand.

## Limits and caveats

- **In memory, per replica.** The default storage lives in the process: with N api replicas the
  effective limit is N × the declared one, and counters reset on deploy. For a strict shared
  limit, plug a shared storage into `ThrottlerModule.forRoot` (e.g. Redis via
  `@nest-lab/throttler-storage-redis`) in `AppModule`; routes don't change.
- **`X-Forwarded-For` can be spoofed.** With `trust proxy: true` a client can prepend a fake IP
  and get a fresh counter. It is good enough as an abuse/risk signal, not as identity. To harden
  it, set `trust proxy` to the exact number of trusted hops (or the proxy ranges) once the real
  chain is confirmed for each path above (they differ by one hop through the store proxy).
- **Don't add named throttlers** (`forRoot([{ name: 'a' }, { name: 'b' }])`): the guard applies
  every named throttler to every guarded route, which then needs `@SkipThrottle({ other: true })`
  everywhere. One `default` throttler + `@Throttle` per route covers it.
- **Domain-level limits are separate.** The throttler counts requests per IP. Per-entity rules
  (e.g. per sale) live in the domain service (see the
  [payment README](https://github.com/merkaly-io/api.merkaly.io/blob/master/src/domain/integration/payment/README.md)).

## Checklist for a new limited route

1. `@UseGuards(ThrottlerGuard)` and `@Throttle({ default: { limit, ttl } })` on the handler, with a
   short inline comment stating the limit in words.
2. If the handler needs the IP, take it with `@Ip()`.
3. Add the route to the table above.
