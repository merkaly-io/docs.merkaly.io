Status: **agreed** (2026-11-25), implemented step by step. payments.merkaly.io becomes the only
service that talks to the payment provider: api.merkaly.io keeps every record (payments, refunds,
withdrawals, chargebacks) and the business rules, and asks this service in Merkaly terms. Transport
rules (envelope, retries, invokes) are the ones of `@merkaly/nest` 0.6 [events](/tecnico/nest/events); this file
only adds what is specific to payments. Types: `src/types/gateway.types.ts`.

The business side (who pays what, statuses as interactive lifecycles, animated flows of charges,
refunds and withdrawals, and the decisions behind this service) is on
[docs.merkaly.io/pagos](https://docs.merkaly.io/pagos).

## Principles

- **Provider agnostic.** The api never sees a provider name, status, unit or credential, and never
  decides with `providerStatus` or `source` (stored and logged only). The service runs one gateway at
  a time behind the `PaymentGateway` port, bound in `PaymentGatewayModule`.
- **Stateless.** No database. The api stores the account access (`PaymentAccountAccess`), the wallet
  and the provider ids of charges and transfers, and sends them back on every invoke. In memory
  caches (main wallet, webhook already synced) are allowed, never needed for correctness.
- **Credentials as a string.** `payment.account.create` answers `credentials`: for now the plain
  subaccount API key (no encryption in this iteration). The api stores it with its own at-rest
  protection and sends it back inside `account`; it never builds or parses it. The final api PR runs
  a one-time script that decrypts the keys stored today into this field.
- **Money in integer cents, instants ISO 8601 UTC, days `YYYY-MM-DD` (Brazil), ids as strings.**
- **Tenant explicit.** The envelope `organization` (`org_...`) travels on every invoke and event; a
  gateway that needs it receives it as `PaymentContext`.
- **References are the api's.** `<orgId>:<saleId>` (charges) and `<orgId>:<withdrawalId>`
  (transfers) are built and parsed by the api; this service only passes them to the provider and back.

## Transport

| From | To | Kind | Exchange | Queue | Message |
| --- | --- | --- | --- | --- | --- |
| webhooks | payments | event (raw provider webhook) | `merkaly.payments` | `merkaly.payments-<provider>` (`.retry`, `.dlq`) | `payment.<provider>.webhook.received` |
| payments | api | event (`payment.*` catalog) | `merkaly.payments` | `merkaly.api-payments` (`.retry`, `.dlq`) | `payment.received`, `payment.transfer.done`... |
| api | payments | invoke | `merkaly.payments` | `merkaly.payments-invokes` | `payment.charge.create`... (catalog below) |
| webhooks | payments | invoke (movement check) | `merkaly.payments` | `merkaly.payments-invokes` | `payment.movement.check` |
| payments | api | invoke (authorize a movement) | `merkaly.api` | `merkaly.api-invokes` | `payment.withdrawal.authorize`, `payment.refund.authorize` |

- webhooks.merkaly.io is only the entry gate: it verifies the provider request and publishes it into
  `merkaly.payments` (`deliver({ service: 'payments', type: 'payment.asaas.webhook.received' }, ...)`); it has no
  payment logic. One message type and one queue per provider: Asaas is
  `payment.asaas.webhook.received` on `merkaly.payments-asaas`, bound with
  `@HandleEvent('payment.asaas.webhook.received', { queue: 'asaas' })` (own exchange, no `from`); a future
  Stripe would be `payment.stripe.webhook.received` on `merkaly.payments-stripe`.
- payments emits the translated events with `emit()` on its own exchange. The api binds them
  `from: 'payments'` on `merkaly.api-payments`.
- Invokes: the caller waits (default 5 s), a lost invoke is never retried by the broker, so every
  write must be safe to repeat (idempotent by `reference`, or checked with a read first, as the api
  does today with `payment.charge.search`).
- Every publish is `mandatory`: the consumer queue must exist before the producer publishes (deploy
  payments first, see Migration).

## Invoke errors

A handler answers the reply type of the catalog. A failure is thrown as an `HttpException` whose
body carries `{ message, code }`; `@merkaly/nest` passes `status`, `message` and `code` through and
the caller's `invoke()` rejects with an `HttpException` of the same status (`getResponse()` =
`{ statusCode, message, code }`). An error that is not an `HttpException` reaches the caller as a
generic 500 and is logged here. Every handler builds them with `paymentException(code, message)`
(`src/exceptions/payment.exception.ts`), which picks the Nest exception of the code; malformed invoke
data is `INVALID_DATA` before any provider call (`src/validators/invoke.validator.ts`). Codes
(`PaymentErrorCode`):

| `code` | `status` | When |
| --- | --- | --- |
| `INVALID_DATA` | 422 | The provider rejected the data (`message` says which field) |
| `REFUSED` | 403 | The provider refused the operation (business refusal) |
| `NOT_FOUND` | 404 | Unknown charge, transfer or account |
| `PIX_UNAVAILABLE` | 503 | The merchant account cannot receive Pix (no Pix key) |
| `NOT_CONFIGURED` | 503 | Main provider key missing or rejected: any invoke answers it (there is no "is configured" invoke) |
| `CREDENTIALS_INVALID` | 503 | `account.credentials` missing or rejected by the provider |
| `RATE_LIMITED` | 503 | The provider rate limited the call |
| `PROVIDER_UNAVAILABLE` | 502 | Provider unreachable, timeout or unexpected answer |

`message` never carries credentials or personal data.

## Invokes answered by payments

Names without the service prefix (the exchange already says who answers): `<entity>.<verb>`. The
table is in the order of the migration groups. "Today in the api" is the method of
`src/domain/integration/payment/providers/asaas` it replaces.

| Type | `data` | Reply `data` | Today in the api | Purpose |
| --- | --- | --- | --- | --- |
| `payment.fees.read` | `{}` | `PaymentFees` | `PaymentAsaasFeeService.fetchFees` | Pix fee of the Merkaly account (and its promotion), read at the api boot |
| `payment.charge.create` | `PaymentChargeCreateRequest` | `PaymentCharge` | `ChargeAdapter.getOrCreateCustomerId` + `createCharge` | Pix charge in the Merkaly account, split to the merchant wallet; finds or creates the customer |
| `payment.charge.read` | `PaymentChargeRequest` | `PaymentCharge` | `ChargeAdapter.getCharge` | Current state of a charge (the sync source of truth) |

| `payment.charge.delete` | `PaymentChargeRequest` | `PaymentChargeDeleted` | `ChargeAdapter.deleteCharge` | Removes a charge still payable (status `PENDING`) |
| `payment.charge.refund` | `PaymentChargeRefundRequest` | `PaymentCharge` | `ChargeAdapter.refundCharge` | Whole or partial refund, part taken back from the merchant split |
| `payment.charge.chargeback.read` | `PaymentChargeRequest` | `PaymentChargeback` | `ChargeAdapter.getChargeChargeback` | Chargeback details (id, deadline, reason) when the embedded one lacks them |
| `payment.charge.pix.read` | `PaymentChargeRequest` | `PaymentChargePix` | `ChargeAdapter.getChargePixDetails` | Pix copy and paste and QR image of a charge |
| `payment.balance.read` | `PaymentBalanceRequest` | `PaymentBalance` | `AccountAdapter.getAvailableBalance` + `getPendingBalance` | Available balance of a merchant account (or the Merkaly one), optionally the pending receivables |
| `payment.transfer.create` | `PaymentTransferCreateRequest` | `PaymentTransfer` | `TransferAdapter.createTransfer`, `createDebtTransfer` | Pix withdrawal to the merchant key, or store debts to the Merkaly account (`PLATFORM`) |
| `payment.transfer.read` | `PaymentTransferReadRequest` | `PaymentTransfer` | `TransferAdapter.getTransfer` | Current state of a transfer |
| `payment.account.create` | `PaymentAccountCreateRequest` | `PaymentAccountCreated` | `AccountAdapter.createAccount` | Merchant account with its notification webhook; answers id, wallet and opaque credentials |
| `payment.account.approval.read` | `PaymentAccountRequest` | `PaymentAccountApproval` | `AccountAdapter.getAccountApproval` | KYC approval per section |
| `payment.account.commercial.read` | `PaymentAccountRequest` | `PaymentAccountCommercialInfo` | `AccountAdapter.getCommercialInfo` | Registration data, prefills the admin form |
| `payment.account.commercial.update` | `PaymentAccountCommercialUpdateRequest` | `{}` | `AccountAdapter.updateCommercialInfo` | Changes merged over the current registration data |
| `payment.account.onboarding.read` | `PaymentAccountRequest` | `PaymentAccountOnboarding` | `AccountAdapter.getOnboarding` | Documents to send and their onboarding links |
| `payment.account.webhook.sync` | `PaymentAccountRequest` | `{}` | `AccountAdapter.syncAccountWebhook` | Creates or rewrites the account notification webhook (url with `?organization=`, token, events) |
| `payment.account.pix_key.ensure` | `PaymentAccountRequest` | `PaymentAccountPixKey` | `AccountAdapter.ensurePixAddressKey` | Creates the receiving Pix key when the account has none (charges split to it need one) |
| `payment.movement.check` | `PaymentMovementCheckRequest` | `PaymentMovementAnswer` | webhooks `AsaasWithdrawalValidator` | Provider asks before money leaves an account (see Movement check) |

Not invokes, they stay in the api: the references (`getChargeReference`, `getChargeSale`, withdrawal
reference parsing), the store name and site (`getStoreName`, tenants), and every credential helper
(`getChargingKey`, `getAccountKey`, `readAccountKey`, `requireEncryptionKey`, `isConfigured`): the
charging key lives only in payments (missing = `NOT_CONFIGURED` on any invoke), the account key
travels as `account.credentials`.

Field notes the implementers rely on:

- `PaymentCharge.status` is the one charge status (`PaymentChargeStatusEnum`), mutually exclusive, the
  only field decided with. Asaas statuses map as: `PENDING` -> `PENDING`; `AUTHORIZED`,
  `AWAITING_RISK_ANALYSIS` and unknown ones -> `IN_PROCESS`; `CONFIRMED` -> `APPROVED` (paid, not
  credited); `RECEIVED` -> `SETTLED`; `RECEIVED_IN_CASH` -> `MANUAL`; `REFUND_REQUESTED`,
  `REFUND_IN_PROGRESS` -> `REFUNDING`; `REFUNDED` -> `REFUNDED`; `CHARGEBACK_REQUESTED`,
  `CHARGEBACK_DISPUTE`, `AWAITING_CHARGEBACK_REVERSAL` -> `DISPUTED` (`CHARGEBACK_LOST` once the
  chargeback is `DISPUTE_LOST`/`DONE`); `OVERDUE` -> `EXPIRED`; deleted -> `CANCELLED` (no separate `deleted` field). The api
  derives the rest: deletable = `PENDING` | `EXPIRED` (an overdue Pix can still be paid, the api
  deletes it before replacing it), paid = `APPROVED` | `SETTLED`, online refund = `APPROVED` |
  `SETTLED`. `MANUAL` is not paid for the api: it never confirms the sale nor buys from the
  supplier, it stays for human review and is refunded by hand. There is no `null`/`UNKNOWN` status:
  `IN_PROCESS` is never paid. `chargeback.stage` keeps the dispute detail (a lost chargeback is
  `LOST` even while the charge still says `CHARGEBACK_*`).
  `providerStatus` is stored for log and audit only and never decided with. A charge whose amount is not money answers
  `PROVIDER_UNAVAILABLE`.
- `PaymentSplit.left` replaces `splitLeftCents`; `PaymentSplit.failed`/`failure` replace
  `splitProblem`. The api picks the merchant split (by `wallet`, or the one with the most `left` as
  today) and sends its `id` back in `payment.charge.refund` `merchant.split`: no second provider read
  inside the invoke.
- `PaymentRefund.description` comes back as sent, so the api keeps telling its refunds apart from the
  ones made in the provider panel. `merchantAmount` replaces `refundedSplits` (`null`: the provider
  gave no split detail, the api keeps its fallback of the whole split); `providerStatus` is the raw
  refund status the api stores today. `merchant` omitted sends no split instruction (the provider
  default), as the api does today when the store gives nothing.
- `PaymentChargeback.stage`: a chargeback reversed in the merchant's favor (Asaas chargeback
  `REVERSED`) is `WON`; `AWAITING_REVERSAL` (charge `AWAITING_CHARGEBACK_REVERSAL`) means won with the
  money on its way back; `LOST` is Asaas `DISPUTE_LOST` or `DONE` (the money went back to the
  cardholder). The charge status decides first, then the chargeback one. Asaas sends no notification
  for the reversal: the api sees `WON` on the next `payment.charge.read`.
- `PaymentChargeback.reason` is the grouped reason (`FinanceChargebackReasonEnum`), `providerReason`
  the raw one; `respondBy` is the end of the last day in Brazil.
- `payment.charge.create`: the due date (today in Brazil), the customer notifications off, the phone
  normalization and the description limit (cut at 500, the api keeps building
  `[number] [orgId] - store` so the tags survive) are gateway details. `split.percentage` is a whole
  percent of the net amount (100 today). Pix refused because the merchant has no key is
  `PIX_UNAVAILABLE` (create and `pix.read`).
- Slow invokes: the provider call times out at 20 s, the Pix QR code at 35 s (slow sandbox). The api
  must pass a `timeout` to `invoke()` above those for `payment.charge.create` and
  `payment.charge.pix.read` (and should for the rest), the 5 s default is too short.
- `payment.fees.read` reads the provider every time (no cache here); the api keeps reading it once at
  boot and caching it as today.
- `payment.balance.read` without `account` reads the Merkaly account (dashboard cash). `pending` is
  slow (pages over the receivables, up to 2000 per provider status), ask it only where shown; it
  answers `null` when the receivables cannot be read (logged here), the available balance still
  answers, as the api warns today. An available balance that is not money is `PROVIDER_UNAVAILABLE`.
- `payment.transfer.create`: the api sends the `description` (today `Saque Merkaly` for
  `PIX_KEY`, `Débitos com a Merkaly` for `PLATFORM`) and the whole Pix key (`pixKeyType` + `pixKey`,
  from its stored account key). `PLATFORM` is an internal transfer to the Merkaly main wallet (read
  once per process here). Not idempotent at the provider: the api keeps creating its withdrawal intent
  first, so the movement check finds it, and does not repeat a lost create blindly.
- `PaymentTransfer` replaces `FinanceWithdrawalTransfer`: `providerStatus` replaces `rawStatus`
  (`UNKNOWN` when missing), `reference` is the raw one (the create answers the sent one when the
  provider omits it) and the api parses `withdrawalId` from it, `createdAt` is ISO UTC (`Date` in the
  api), `provider` is gone (the api stores its own). `status: null` stays unknown, never done.
- `movement.search` needs no invoke: it only reads stored charges. Its provider raw statuses
  (`ASAAS_UNSETTLED_CHARGE_STATUSES`) go away with the `PaymentCharge.status` the api stores
  (`SETTLED` vs `APPROVED`).
- `payment.account.create` and `payment.account.webhook.sync` read `organization` from the envelope
  (the webhook url carries it, missing is `INVALID_DATA`). `credentials: null` means the provider gave
  no key: the account needs support, as today. `holder` is the one the api resolves today (the
  caller's personal data for `INDIVIDUAL`, `birthDate` required; the body for `COMPANY`,
  `companyType` required) and `site` the store url, both built by the api (tenants, Auth0).
- The account webhook (url `ASAAS_WEBHOOK_URL?organization=`, token `ASAAS_WEBHOOK_TOKEN`, account
  status and transfer events) is created with the account and synced at most once per replica; with
  the token unset both skip it (logged once). `payment.account.webhook.sync` rejects when the provider
  fails (the api adapter swallowed it: the api catches and logs to keep that).
- `payment.account.approval.read` answers `PROVIDER_UNAVAILABLE` on an unknown section status.
  `payment.account.commercial.update` answers `INVALID_DATA` when neither the changes nor the account
  have a monthly income; `birthDate`, document and person type never change.
- `payment.account.pix_key.ensure` answers the coarse `status` (`ACTIVE`, `PENDING` for any other live
  key, `null` none): the api stored the raw provider status, it stores this one now (`pixReady` = not
  `null`, skip the call once `ACTIVE`). A provider failure answers `{ status: null }` (logged) as the
  adapter did, but `NOT_CONFIGURED` and `CREDENTIALS_INVALID` are thrown: the api turns them into
  `accountError` (it can no longer tell an unusable key before calling).
- Missing or rejected `account.credentials` is `CREDENTIALS_INVALID` on every account invoke (the api
  `readAccountKey` error).
- If an implementation needs a field that is not here, add it to this file and to
  `gateway.types.ts` in the same PR.

## Provider notifications (webhooks → payments → api)

| Type | Exchange | Queue | `organization` | `data` |
| --- | --- | --- | --- | --- |
| `payment.asaas.webhook.received` | `merkaly.payments` | `merkaly.payments-asaas` | when the edge resolves it (`externalReference`, `?organization=`) | `ProviderNotification`: `{ payload, organization? }`, the provider body without the buyer's personal data |

The type names the provider, so this message needs no `source`. The emitted `payment.*` events keep
`source` (and the `<provider>:<event id>` id) as they have today, for audit only.

The gateway (`translateNotification`) turns the payload into the existing `payment.*` catalog
(`@merkaly/nest` [events](/tecnico/nest/events), section 7) and emits it on `merkaly.payments` with the same `type`,
`data`, `id` (`<provider>:<provider event id>`), `source`, `organization`, `occurredAt` and `raw` as webhooks
publishes today: the api listeners do not change, only their binding (`from: 'payments'`). A payload
outside the catalog is acked with a warning (`NotificationIgnoredException`), a translation that
should have worked is logged as an error.

## Movement check (webhooks → payments → api)

Some providers ask before money leaves an account (Asaas: withdrawal validation for `TRANSFER` and
`PIX_REFUND`). The answer must arrive in a few seconds, so it is invoke end to end:

1. webhooks invokes `payment.movement.check` with `{ payload }` (the provider body), timeout 3 s.
2. The gateway reads it (`readMovementCheck`) into `PaymentMovementCheck`; unreadable or an
   unsupported kind is refused without asking the api. For a refund it also reads the refunded
   charge to add its reference (see Timing).
3. payments invokes the api, timeout 2 s at most, with:
   - `TRANSFER`: `payment.withdrawal.authorize` with `{ transfer: { id, amount, externalReference, operationType } }`
   - `REFUND`: `payment.refund.authorize` with `{ refund: { id, payment, amount, reference, organization } }`:
     `payment` the refunded charge id, `reference` its reference (`<orgId>:<saleId>`, what the api
     sent in `payment.charge.create`), `organization` the `orgId` parsed from it. Both `null` when
     the charge could not be read in time or has no Merkaly reference: the api refuses, it never
     reads the charge back.

   (cents, never the Pix key or bank account). The api answers `PaymentMovementVerdict`
   (`{ status: 'APPROVED' }` or `{ status: 'REFUSED', refuseReason }`).
4. The gateway turns the verdict into the body the provider expects (`answerMovementCheck`) and
   payments replies `PaymentMovementAnswer` (`{ approved, body }`); webhooks answers the provider with `body`.

Any failure or timeout on the way is a refusal, never a 5xx to the provider: payments refuses when
the api does not answer, webhooks refuses when payments does not answer.

Implemented in `MovementInvokesController` (`src/controllers/movement.invokes.controller.ts`), the
handler never throws:

- Timing: webhooks waits 3 s. The Asaas `PIX_REFUND` body has no `externalReference`, so the gateway
  reads the charge (`GET /payments/{payment}`, main key) capped at 800 ms; a failure or timeout is
  logged as a warning and sends `reference: null`. The api invoke gets what is left of 2.5 s from the
  start of the check, 2 s at most (at least 1.7 s after a refund read), leaving 0.5 s for the
  broker hops back to webhooks. Transfers read nothing and keep the full 2 s.
- Asaas body (`AsaasMovementCheckPayload`): `{ type: 'TRANSFER', transfer: { id, value, externalReference, operationType } }`
  or `{ type: 'PIX_REFUND', pixRefund: { id, payment, value } }`; `value` in reais becomes cents
  (`asaasToCents`, more than 2 decimals is `null` and the api refuses it). Any other `type` or no id
  is refused with `Merkaly validates only withdrawals and Pix refunds` (logged as a warning with the type).
- The api invoke carries the `source` and `correlationId` of the webhooks invoke, no `raw`. A late,
  failed or malformed api answer is refused with `Merkaly could not validate the withdrawal` or
  `Merkaly could not validate the Pix refund`; an unreadable body with
  `Merkaly could not read the validation request`.
- Asaas answer (`answerMovementCheck`): `{ status: 'APPROVED' }` or
  `{ status: 'REFUSED', refuseReason }`, with HTTP 200; webhooks returns `body` as is.

## Migration (each step deployable alone)

1. **This service on `@merkaly/nest` 0.5** (this PR): consumes `merkaly.payments-asaas`, declares
   `merkaly.payments-invokes` (no handler yet), emits on `merkaly.payments`. Deploy it first: nothing
   reaches it until webhooks switches.
2. **Notifications**: the api binds the `payment.*` events `from: 'payments'`, then webhooks stops
   translating Asaas and publishes `payment.asaas.webhook.received` into `merkaly.payments`. The package
   binds and never unbinds, so the old `merkaly.webhooks` bindings of `merkaly.api-payments` keep
   delivering during the switch; remove them by hand once webhooks is deployed.
3. **Invokes**, one PR per group in this repo (handlers plus the Asaas gateway methods): fees;
   charges (create, read, search, delete, pix); refunds and chargeback; balance and transfers;
   account (create, approval, commercial, onboarding, webhook, Pix key); movement check.
4. **api swap**: one api PR replaces every adapter call with the invoke, runs the one-time script
   that decrypts the stored subaccount keys into `credentials`, and deletes
   `providers/asaas` and the `ASAAS_*` variables; webhooks invokes `payment.movement.check` instead
   of the api and drops its Asaas translation.
