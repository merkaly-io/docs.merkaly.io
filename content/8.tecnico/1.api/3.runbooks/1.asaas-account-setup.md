How to set up a Merkaly main account at Asaas from zero: a new production account, or a sandbox
account recreated to wipe its data (Asaas offers no other way to reset a sandbox). A new account
has nothing: no Pix key, no API key, no webhooks, no withdrawal validation. Nothing carries over
from a deleted account or between sandbox and production.

Since the payments cut, the gateway code lives in payments.merkaly.io (its README and
[contract](/tecnico/payments/contract)); the api keeps the records and asks payments over RabbitMQ
([Payment](https://github.com/merkaly-io/api.merkaly.io/blob/master/src/domain/payment/README.md)). This runbook should move
to payments.merkaly.io. Business side:
[docs.merkaly.io/pagos](https://docs.merkaly.io/pagos).

| | Sandbox | Production |
|---|---|---|
| Panel | https://sandbox.asaas.com | https://www.asaas.com |
| API (`ASAAS_BASE_URL`) | `https://api-sandbox.asaas.com/v3` | `https://api.asaas.com/v3` |

## 1. Create the account

- Account type **company (CNPJ)**. Asaas refuses subcontas to individual (CPF) accounts: the admin
  then gets a 422 with the Asaas message. A new sandbox account may come as Pessoa Física; switch it
  in Minha conta > Informações > Dados comerciais: Tipo da conta **Pessoa Jurídica**, CNPJ, Tipo de
  empresa, Nome da empresa, then Salvar alterações. Check this first: everything below stays.
  Asaas analyses the change (up to 2 business days); until then the API still treats the account
  as an individual and refuses subcontas. In the sandbox, ask integracoes@asaas.com.br to approve
  it right away. Simpler: create the sandbox account as a company from the start.
- Sandbox: the token for critical actions is always `000000`.

## 2. Pix key of the main account

Charges are created in the main account (100% split to the subconta), so the main account needs
**one active Pix key**. Without it every Pix charge fails with 422.

Panel: Pix > Minhas chaves > Cadastrar chave > Continuar, type **Chave aleatória**, Cadastrar. The
key is sent to the Central Bank and becomes active shortly after.

Each subconta needs its own Pix key too (else Asaas answers `invalid_action`): nothing to do by
hand, the api asks payments for one on the account refresh (`payment.account.pix_key.ensure`, see
"Store account Pix key" in the [payment README](https://github.com/merkaly-io/api.merkaly.io/blob/master/src/domain/payment/README.md)).

## 3. API key

Panel: Integrações (account menu, top right) > Chaves de API > generate a key. Copy it right away: Asaas shows it only once.
It goes to `ASAAS_API_KEY` (step 8). Never paste it in a ticket, chat or commit.

## 4. Payments webhook

One webhook on the main account receives every charge event (subcontas never see them). Asaas keeps
at most 10 webhooks per account.

Panel: Integrações > Webhooks > Adicionar Webhook:

| Field | Value |
|---|---|
| Name | `Merkaly payments` |
| URL | `https://webhooks.merkaly.io/asaas` |
| Email | `notifications@merkaly.io` |
| API version | v3 |
| Send type | Sequential |
| Auth token | the value of `ASAAS_WEBHOOK_TOKEN` (step 8) |
| Enabled | yes, not interrupted |
| Events | **all of them** ("Selecionar Todos" in every section) |

Merkaly selects every event: `webhooks.merkaly.io` answers 200 to the ones it does not use (logged
as a warning), and a new use never needs a panel change. Some Pix Automático events stay disabled
until Asaas enables the product; leave them. Account (`ACCOUNT_STATUS_*`) and transfer (`TRANSFER_*`)
events of the main account carry no organization and are discarded (logged as an error); the
subcontas have their own webhooks (step 9).

The events the api actually needs (minimum, if a list is ever required):

```text
PAYMENT_CREATED
PAYMENT_UPDATED
PAYMENT_AUTHORIZED
PAYMENT_AWAITING_RISK_ANALYSIS
PAYMENT_APPROVED_BY_RISK_ANALYSIS
PAYMENT_REPROVED_BY_RISK_ANALYSIS
PAYMENT_CONFIRMED
PAYMENT_RECEIVED
PAYMENT_OVERDUE
PAYMENT_DELETED
PAYMENT_RESTORED
PAYMENT_REFUNDED
PAYMENT_PARTIALLY_REFUNDED
PAYMENT_REFUND_IN_PROGRESS
PAYMENT_REFUND_DENIED
PAYMENT_CHARGEBACK_REQUESTED
PAYMENT_CHARGEBACK_DISPUTE
PAYMENT_AWAITING_CHARGEBACK_REVERSAL
PAYMENT_SPLIT_CANCELLED
PAYMENT_SPLIT_DIVERGENCE_BLOCK
PAYMENT_SPLIT_DIVERGENCE_BLOCK_FINISHED
PAYMENT_SPLIT_DONE
```

Or by API (same result), with the key of step 3:

```http
POST {ASAAS_BASE_URL}/webhooks
access_token: <ASAAS_API_KEY>
Content-Type: application/json

{
  "name": "Merkaly payments",
  "url": "https://webhooks.merkaly.io/asaas",
  "email": "notifications@merkaly.io",
  "enabled": true,
  "interrupted": false,
  "apiVersion": 3,
  "authToken": "<ASAAS_WEBHOOK_TOKEN>",
  "sendType": "SEQUENTIALLY",
  "events": ["PAYMENT_CREATED", "...the list above..."]
}
```

## 5. Withdrawal validation

Asaas asks Merkaly before each API transfer of any subconta; the api approves only the withdrawals
it started (see Withdrawals in the payment README).

Panel: Integrações > Segurança > Validação de saque via Webhook > Habilitar validação, then Salvar:

| Field | Value |
|---|---|
| URL | `https://webhooks.merkaly.io/asaas/withdrawals` (**with `/withdrawals`**) |
| Auth token | the same `ASAAS_WEBHOOK_TOKEN` |
| Email | `notifications@merkaly.io` |
| Validate also interface withdrawals | unchecked |
| Splits | unchecked |
| Pix refunds | checked once the IP whitelist (5.1) is on |

Pointing it at `/asaas` or using another token refuses every withdrawal.

Both forms (steps 4 and 5) are lost when leaving the page before Salvar: open them in separate tabs
when doing both at once.

### 5.1 IP whitelist (no manual approval)

By default every withdrawal asked through the API (transfers, Pix refunds, the store debt transfers)
becomes a **critical event** that waits for a manual approval with a token in the panel or the app
(`AWAITING_CRITICAL_ACTION_AUTHORIZATION`). Without this step no automatic refund or debt transfer
completes. The webhook validation of step 5 does not remove it: it is an extra check, not the
approval. Subcontas inherit the setting of the main account.

1. Give payments.merkaly.io a fixed outbound IP in Railway (service > Settings > Networking >
   Static Outbound IPs) and note the addresses. Without a fixed IP, Asaas offers a form for
   accounts that cannot whitelist (ask the account manager).
2. Panel: Integrações > Segurança > Whitelist de IPs > add each payments IP.
3. Same page, "Evento crítico em requisições de saque": **Desativado**. Requests from the
   whitelisted IPs are then processed without manual approval; any other IP is refused.
4. Step 5: check **Pix refunds**, so every refund is still validated by the api
   (`payment.refund.authorize`) now that no human approves it.
5. Check: cancel a paid test sale; the refund reaches `DONE` without a token and the api logs
   `payment.refund.authorize` `APPROVED`.

Sources: [Whitelist de IPs](https://docs.asaas.com/docs/whitelist-de-ips),
[Validação de saque via webhooks](https://docs.asaas.com/docs/mecanismo-para-validacao-de-saque-via-webhooks).
Changing the Railway region or plan can change the outbound IP: update the whitelist with it.

## 6. Payment split

Charges carry a 100% split to the subconta wallet, so the main account must have Split enabled.
Without it the charge with split is refused.

Panel: Integrações > Segurança > Habilitar Split de pagamento > Habilitar Split, confirmed by token
or SMS (sandbox: `000000`). Disabling it later needs Asaas support.

## 7. White label (BaaS)

With BaaS the merchant never sees Asaas: no activation email, no Asaas login, and the KYC documents
come with an `onboardingUrl` that the admin opens. Without it, Asaas emails each merchant an
activation link with the Asaas brand, and the documents come without `onboardingUrl`. It only
applies to subcontas created after it is enabled.

**Sandbox** (panel, no one to ask): user menu > Minha conta > Configurações > Sandbox. Each field has
its own Salvar; reload the page afterwards and check they kept the value.

| Field | Value |
|---|---|
| Habilitar White Label para subcontas | Sim |
| Habilitar autoaprovação de subcontas (Configurações para testes) | Sim (subcontas approve themselves, the store offers Pix right away) |
| Modelo da operação | **Cliente Baas** (the default "Não quero operar com subcontas" keeps the subconta restrictions) |
| Tokenização de cartão, pagadores estrangeiros, limites de cobrança | not used (Pix only), leave as they are |

Auto-approval is a sandbox simulation: production always runs the real review.

**Production**: not in the panel. Ask the Asaas account manager (WhatsApp 0800 009 0037) to enable
BaaS; assume a new account does not inherit it. Asaas sends a compliance Playbook: by RC 16/2025 the
Asaas brand, links and responsibility texts must be shown at every merchant touch point (screens,
receipts, onboarding, contracts). The regulatory evaluation period applies (10 subcontas, R$ 2.000,00
per subconta, 60 days).

## 8. Railway variables

| Service | Variable | Value |
|---|---|---|
| payments | `ASAAS_BASE_URL` | the API url of the table above (unset falls back to the sandbox) |
| payments | `ASAAS_API_KEY` | the key of step 3 |
| payments | `ASAAS_WEBHOOK_TOKEN` | the token used in steps 4 and 5 |
| webhooks | `ASAAS_WEBHOOK_TOKEN` | **exactly the same value** as payments |
| api, payments, webhooks | `RABBITMQ_URL` | the same broker (invokes and the withdrawal validation go over it) |

The api has no `ASAAS_*` variable: the payment provider configuration lives in payments.merkaly.io. Changing a variable redeploys the service. Changing `ASAAS_WEBHOOK_TOKEN` also
requires updating the token in steps 4 and 5; store account webhooks are rewritten on the next
status read (`payment.account.webhook.sync`).

Local: a local api talks to whatever payments consumes the shared broker. Asaas cannot reach a
local webhooks service without a tunnel, so a local api only gets events through the reads of open
charges (about a minute) and its withdrawals are refused while the validation of step 5 is on.

## 9. Subconta webhooks

Nothing by hand. payments registers the `ACCOUNT_STATUS_*` and `TRANSFER_*` webhooks of each
subconta when it creates it.

## 10. Organizations with a subconta of the old account

Every organization that had a subconta keeps it in its database (`settings`, key `payments`), pointing to an account that no longer exists, so its status reads fail. Its merchant
must create the subconta again from the admin (Integrações > Pagamentos), which answers 409 while
the old one is stored. Clear the stored `account` of those organizations first.

The Mongo cluster is shared with production: list the organizations and confirm with the Founder
before changing anything. Old `finance.payments` and `finance.withdrawals` rows refer to charges and
transfers of the deleted account; they stay as history.

Deleting a main account does not delete its subcontas, and Asaas keeps a CPF/CNPJ in one account
only: creating the subconta again with the same document fails with `O CPF ... já está em uso
(invalid_object)`. Ask integracoes@asaas.com.br to close the old subconta or release the document.

Sandbox notes: subconta emails (activation, documents) go to the main account email, and the
sandbox allows up to 20 subcontas per day.

**Wrong data in a subconta** (e.g. a mistyped email): Editar dados in the admin changes only the
contact data; the registration email (activation and login, shown in the Asaas panel under Dados da
Subconta) never changes, and name, CPF and birth date are locked. Close the subconta and create it
again:

1. Asaas panel (main account), the subconta > Dados da Subconta > Encerrar subconta. Free within
   48 hours if it never logged in. By API (non-BaaS): `DELETE /v3/accounts/{id}` with the main key,
   within 48 hours and never logged in, after enabling Integrações > Segurança > Validação de
   encerramento de subcontas pela API and the IP whitelist (Railway has no fixed outbound IP by
   default). BaaS subcontas: `DELETE /v3/myAccount` with the subconta key (no balance, no open
   charges or withdrawals).
2. Clear the stored `gateway` (and `error`) of that organization in `settings` key `payments`
   (shared cluster: confirm with the Founder first).
3. The merchant creates the subconta again from the admin.

## 11. Smoke test

1. Admin, Integrações > Pagamentos: create a subconta (sandbox: approve it in the panel; path not
   verified yet).
2. Store: buy something with Pix. Sandbox: confirm the payment in the panel (path not verified yet; was Cobranças > the charge >
   Confirmar recebimento). The sale must become paid within seconds; `railway logs -s
   webhooks.merkaly.io --http --filter '@path:/asaas'` shows `POST /asaas 200`.
3. Admin: withdraw a small amount. Sandbox: use an Asaas test key (`cliente-a00001@pix.bcb.gov.br`,
   see the payments.merkaly.io docs). The webhooks logs show `POST /asaas/withdrawals 200`
   about 5 s after the transfer is created, the api logs `payment.withdrawal.authorize` with
   `APPROVED`, and the panel (Validação de saque > Logs das autorizações) shows it approved.

A refused withdrawal (`Autorização externa foi recusada.`) is diagnosed with the payments.merkaly.io
docs (the movement check logs in payments and the api).
