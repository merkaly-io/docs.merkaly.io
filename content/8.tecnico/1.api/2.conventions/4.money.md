---
title: 'Money convention: integer cents'
description: 'Every monetary value is an integer in cents.'
---

> **Rule:** every monetary value in Merkaly is an **integer in the minor unit (cents)**.
> `$1.00` is stored, transported and computed as `100`. Never use floats for money.

## Why

Floating-point arithmetic introduces rounding errors (`0.1 + 0.2 !== 0.3`). Keeping
money as integer cents makes every sum, multiplication and comparison exact. The
conversion to a human-readable string happens **only at the presentation layer**.

## Where it applies

Any field representing an amount of money is an integer of cents, e.g.:

- Catalog: `product.price` / `sellPrice`, `product.cost` / `buyPrice`, `variant.price`
- Orders: item `price.product` / `price.variant`, line/order totals
- Finance: `payment.amount`, `payment.fee`, `invoice.total` / `subtotal` / `tax`, `refund.amount`
- Derived metrics: `inventoryValue`, blocked-sales `amount`, cashFlow, etc.

Entities enforce this with `@Prop({ ..., validate: { validator: Number.isInteger } })`.
Counts and quantities (units, product counts) are **not** money — they are plain
integers and must not be divided by 100.

## Formatting (frontend)

Two distinct helpers — do not mix them up:

| Helper | Divides by 100 | Currency symbol | Use for |
|--------|----------------|-----------------|---------|
| `formatMoney(value, opts)` / `MKFormatMoney` | ✅ yes (`base`, default 100) | ✅ yes | **money** (cents in → `$1.00` out) |
| `formatNumber(value, opts)` / `MKFormatNumber` | ❌ no | ❌ no | counts, units, percentages |

- `formatMoney(100)` → `"$1.00"`. `formatMoney` accepts `notation` and
  `maximumFractionDigits` for compact currency (`$124K`) — use these instead of
  reaching for `formatNumber` with `style: 'currency'`, which **skips the /100** and
  renders the amount 100× too large.
- In templates use the component (`MKFormatMoney` / `MKFormatNumber`); in scripts that
  build a string (e.g. arrays of card values) use the function.
- Never write a manual `/ 100` or `* 100` next to a formatter — the formatter owns the
  conversion. Manual conversion + `formatMoney` double-divides.

## Input

When a user types an amount in a form, multiply by 100 before sending to the API, and
divide by 100 only for display. The wire format and the DB are always cents.

## Sale profit

`OrderSaleEntity.cost` and `profit` (cents, admin sales list, dashboard home) and the admin
summary (`GET /orders/sales/:id/summary`) share one calculation, `src/domain/order/utils/sale.profit.ts`,
so the list and the sale sheet always show the same profit. Costs come only from stored snapshots,
so later catalog price changes never alter them:

- `cost` = sum of the live purchases of the sale (not deleted, not `CANCELLED`): items at the
  supplier cost snapshot + `shippingCost` + `taxCost` (import tax) estimated at procurement. `0` once the sale is closed
  (`cancelledAt`, or every purchase cancelled): nothing will be bought.
- `profit` = `pricing.total` (what the buyer pays: items + buyer freight + import taxes) − refunded − `cost` −
  refund fees (`getSaleProfit`). Refunded is every refund of the sale payment (returned or still
  owed), capped at `pricing.total`; refund fees are the `REFUND_FEE` debts of the payment.
- Margin is `profit` over `pricing.total` − refunded; `null` when that base is not positive.
- Both are `null` while the sale has no live purchase and is not closed (not ordered at the
  supplier yet; the summary shows the catalog estimate instead).
- The buyer payment fee is **not** part of the revenue.
- They need `SALE_PROFIT_JOIN` (purchases, payment with `refunds` and `refundFeeDebts`): one
  populate query per path for the whole page, never per row. Without it they are `undefined`.
- They are virtuals, so Mongo aggregations cannot sort or group by them.
