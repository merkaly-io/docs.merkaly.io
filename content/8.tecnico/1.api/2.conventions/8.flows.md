Un flow (`src/domain/<dominio>/flows/<entidad>.<acción>.flow.ts`) orquesta un caso de negocio: decide
qué pasos corren, en qué orden, con qué condiciones y qué hacer ante un fallo. Esta página fija **cómo
se escribe por dentro**. Dónde vive cada capa y qué hace cada tipo de archivo está en
[Layers and file roles](/tecnico/api/conventions/layers).

## Para qué

- Cualquiera abre un flow y entiende el caso leyendo **un solo método**, de arriba abajo.
- Todos los flows se llaman igual desde afuera (`execute(request)`), así que controllers, listeners y
  otros flows no dependen de nombres sueltos.
- Cada decisión tiene nombre propio (`assertProductHasNoOrders`), así que se lee, se prueba y se
  revisa por separado.

## Las reglas

1. **Firma.** El flow extiende `AbstractFlow<TRequest, TResult>`
   (`src/infrastructure/abstracts/abstract.flow.ts`), que declara
   `public abstract execute(request: TRequest): Promise<TResult>`. Un solo parámetro, de un tipo con
   nombre (`<Dominio><Entidad><Acción>Request`, exportado junto al flow; reutiliza el `*Request` que ya
   exista). Si necesitas opciones, van dentro del request.
2. **Una sola entrada.** `execute` es el único método público y lo único que se llama desde afuera
   (controllers, listeners, otros flows). No hay otros métodos públicos.
3. **`execute` se lee lineal.** Describe qué operaciones corren y en qué orden. Todo lo demás son
   helpers privados; cada uno responde **una** pregunta de la lógica y le devuelve a `execute` un
   resultado simple.
4. **Prefijos de helpers.** `assert*`, `resolve*` o `apply*` (tabla abajo). Ningún otro.
5. **Dependencias.** Todo `@Inject()` es `protected readonly` (abierto a extensión). Igual se prefiere
   la composición: un flow que necesita otro lo inyecta y llama su `execute`, nunca lo extiende.
6. **El flow decide, los servicios hacen.** Los servicios y repositorios persisten, leen y llaman a
   proveedores. Los helpers arman sus respuestas usando servicios; una regla que pertenece a la
   decisión (por ejemplo "no se borra la variante por defecto") vive en el flow, no escondida en un
   servicio.
7. **Errores.** `execute` usa `await` lineal. Si un paso tiene que capturar un error, el `.catch` vive
   dentro de su helper, nunca en `execute` (y `.then/.catch` antes que `try/catch`, ver
   [Async errors](/tecnico/api/conventions/async-errors)).
8. **Transacciones.** `@Transactional()` va en `execute` cuando el flow escribe. Lo que solo debe
   ocurrir si la transacción se confirma (avisar a un proveedor, publicar un evento) se agenda con
   `afterCommit(work)`.
9. **Forma.** Máximo dos parámetros por método (tres si el tercero es de opciones), nombres
   explícitos, comentarios cortos al final de la línea y `LoggerService` inyectado (`this.$logger`).

## Prefijos de helpers

| Prefijo | Responde | Devuelve | Ejemplo |
|---|---|---|---|
| `assert*` | ¿Se cumple esta condición? Si no, lanza | `void` | `assertProductHasNoOrders(productId)` |
| `resolve*` | ¿Cuál es este dato? | El dato | `resolveLockedProductId(locator)` |
| `apply*` | Hace un cambio | Nada o lo que el cambio produjo | `applySaleCancellation(sale)` |

Los helpers son privados y no deciden el orden: eso es de `execute`.

### Nombres que se leen como una frase

El nombre dice **sobre qué cosa** actúa y **qué comprueba, devuelve o cambia**, para que `execute` se entienda
sin abrir los helpers. No basta con el estado (`assertAwaitingPayment`): hace falta el sujeto.

| Prefijo | Forma | Así no | Así sí |
|---|---|---|---|
| `assert` | `assert` + sujeto + `Is`/`Are`/`Has`/`Can`/`Matches` + condición | `assertAwaitingPayment` | `assertSaleIsAwaitingPayment` |
| | | `assertCartAvailable` | `assertCartItemsAreAvailable` |
| | | `assertNotDefaultVariant` | `assertVariantIsNotDefault` |
| | | `assertVerifiedEmail` | `assertUserEmailIsVerified` |
| `resolve` | `resolve` + qué devuelve + de dónde o para qué | `resolveSale` | `resolveSaleToCancel` |
| `apply` | `apply` + acción + sujeto | `applySync` | `applyPaymentSyncFromCharge` |

```ts
await this.assertSaleIsAwaitingPayment(sale);
const charge = await this.resolveChargeOfSale(sale);
await this.applyPaymentSyncFromCharge(charge);
```

La regla de lint solo controla el prefijo; que el nombre se entienda se revisa en el PR.

## Antes y después: `product.delete`

Antes, un método público con nombre propio delegaba en un método privado transaccional que mezclaba
el bloqueo, la regla y el borrado:

```ts
@Injectable()
export class CatalogProductDeleteFlow extends AbstractFlow {
  @Inject() private readonly $products: CatalogProductService;
  @Inject() private readonly $purchases: OrderPurchaseRepository;
  @Inject() private readonly $sales: OrderSaleRepository;

  public deleteProduct(locator: EntityLocator<CatalogProductEntity>) {
    return this.applyProductDelete(locator);
  }

  @Transactional()
  private async applyProductDelete(locator: EntityLocator<CatalogProductEntity>) {
    const product = await this.$products.lockProductForDelete(locator);
    const productId = String(product._id);

    if (
      (await this.$purchases.hasOrdersWithProduct(productId)) ||
      (await this.$sales.hasOrdersWithProduct(productId))
    ) {
      throw new ConflictException('Cannot delete product with related orders');
    }

    await this.$products.deleteLockedProduct(productId);
  }
}
```

Después, `execute` cuenta el caso en tres líneas y cada pregunta tiene su helper:

```ts
export interface CatalogProductDeleteRequest {
  product: EntityLocator<CatalogProductEntity>;
}

@Injectable()
export class CatalogProductDeleteFlow extends AbstractFlow<CatalogProductDeleteRequest> {
  @Inject() protected readonly $products: CatalogProductService;
  @Inject() protected readonly $purchases: OrderPurchaseRepository;
  @Inject() protected readonly $sales: OrderSaleRepository;

  @Transactional()
  public async execute(request: CatalogProductDeleteRequest): Promise<void> {
    const productId = await this.resolveLockedProductId(request.product);

    await this.assertProductHasNoOrders(productId);

    await this.$products.deleteLockedProduct(productId); // sus variantes en la misma transacción
  }

  private async resolveLockedProductId(locator: EntityLocator<CatalogProductEntity>): Promise<string> {
    const product = await this.$products.lockProductForDelete(locator);

    return String(product._id);
  }

  private async assertProductHasNoOrders(productId: string): Promise<void> {
    if (await this.$purchases.hasOrdersWithProduct(productId)) {
      throw new ConflictException('Cannot delete product with related orders');
    }

    if (await this.$sales.hasOrdersWithProduct(productId)) {
      throw new ConflictException('Cannot delete product with related orders');
    }
  }
}
```

El controller llama siempre igual:

```ts
await this.$deleteFlow.execute({ product: id });
```

En `variant.delete` la regla "no se borra la variante por defecto" estaba dentro de
`CatalogVariantService.lockVariantForDelete`; ahora el servicio solo bloquea y devuelve la variante con
su producto, y el flow decide con `assertNotDefaultVariant` (regla 6).

## `afterCommit`

`afterCommit(work)` (helper protegido de `AbstractFlow`) agenda trabajo para **después** de que la
transacción en curso se confirme:

- Dentro de una transacción, `work` se encola en la lista `afterCommit` del CLS, la misma que usan las
  reacciones de `@Listen`. `MongoService.transaction` (lo que corre detrás de `@Transactional()`) la
  vacía después del commit, una a la vez. Si la transacción hace rollback, o se reintenta, la lista se
  descarta y `work` no corre.
- Sin transacción, `work` corre en el momento.
- Nunca rechaza: si `work` falla, se registra en el log y no se deshace lo ya confirmado.
- Corre en el mismo contexto del request (misma organización y usuario), ya sin sesión.

Ejemplo (ilustrativo, los flows de catálogo no lo necesitan):

```ts
@Transactional()
public async execute(request: OrderSaleReceiptRequest): Promise<void> {
  const sale = await this.resolveReceivableSale(request.sale);

  await this.applyDelivered(sale);

  await this.afterCommit(() => this.$supplier.confirmReceipt(sale)); // solo si se confirma
}
```

Llamar al proveedor directo en `execute` lo haría **dentro** de la transacción: si después algo falla
y se hace rollback, el proveedor ya quedó avisado de algo que no pasó.

## Composición

Un flow que necesita otro lo inyecta y llama su `execute`; nunca lo extiende ni llama sus helpers:

```ts
@Inject() protected readonly $refundFlow: OrderSaleRefundFlow;

await this.$refundFlow.execute({ sale }); // dentro de la misma transacción si este execute es @Transactional()
```

## Lint

La regla local `merkaly/flow-structure` (`.eslint/flow.plugin.mjs`, configurada en
`eslint.config.mjs` para `src/**/*.flow.ts`) avisa cuando un flow:

- no declara `execute`, o `execute` recibe más de un parámetro;
- tiene otro método público;
- tiene un helper sin prefijo `assert`, `resolve` o `apply`;
- tiene un `@Inject()` que no es `protected readonly`.
