---
title: 'Search queries'
description: 'filters, sort, pagination, join and select on search endpoints.'
---

`GET` search endpoints read `filters`, `sort`, `pagination`, `join` and `select` from the query through
`SearchValidator` (`src/infrastructure/abstracts/abstract.validator.ts`). Read, create and update endpoints
read `join` and `select` through `ReadValidator`.

## Whitelist per endpoint

`filters`, `sort` and `join` are **deny by default**. Each endpoint that lets clients filter, sort or join
uses its own validator with a static `rules` list (join, filters and sort in the same object):

`sort` is optional: when omitted, a client may sort by the same fields it may filter by (a filterable
field leaks nothing new through ordering). Declare `sort` only when it differs, e.g. `createdAt`.


```ts
// src/application/store/catalog/validators/product.request.validator.ts
export class StoreSearchProductsRequestValidator extends SearchValidator<CatalogProductEntity> {
  public static override readonly rules: SearchRules = {
    filters: ['_id', 'brand', 'category', 'name', 'retailPrice'],
    join: ['category', 'variants', 'variants.picture'],
    sort: ['createdAt', 'name'],
  };
}

// src/application/store/catalog/validators/product.request.validator.ts
export class StoreReadProductRequestValidator extends ReadValidator {
  public static override readonly rules: ReadRules = { join: ['brand', 'category', 'variants'] };
}
```

- Only listed fields, wrapped at most in `$and` / `$or`.
- Operators: `$eq $ne $in $nin $gt $gte $lt $lte $regex $options $exists`, with plain values (no nested operators).
- Anything else is a 400 that names the field or operator, never the value.
- Endpoints that use the plain `SearchValidator` / `ReadValidator` accept no `filters`, `sort` or `join` at all.
- The repository adds `deletedAt: null` last, so a filter can never bring deleted documents back.

When a frontend needs a new filter or join, add it to that endpoint's `rules` (only what the screen sends).
Server-side conditions (buyer scope, `active: true` on the Store) and server-side joins are added by the
controller after validation.

## Pagination

- `pagination.page` must be at least 1 and `pagination.limit` between 1 and 100 (`PAGINATION_MAX_LIMIT`);
  defaults are page 1, limit 10. Anything else is a 400.
- `limit: -1` or `page: -1` (every record in one page) is denied by default. An endpoint allows it with
  `unlimited: true` in its `rules`, only for small collections a screen needs whole (category tree,
  brand lists).
- Server-side calls to `AbstractRepository.search` are not validated and may still pass `limit: -1`.

## Where validators live

- **Query validators** (read and search, the ones with `rules`) belong to the application, never the domain:
  `src/application/<surface>/<module>/validators/<entity>.request.validator.ts` (one file per entity holding its
  Read, Search, etc. classes), next to the controller folder
  (e.g. `src/application/admin/catalog/validators/product.request.validator.ts`).
- Each surface (admin, store, dashboard, www) declares its own, even when another surface has the same list,
  so every surface sets its join, filters and sort independently. Never import another surface's validator.
- **Payload validators** (create and update bodies) stay in the domain (`src/domain/<x>/validators/`).
- When a query shape is published in `@merkaly/api` (listed in `packages/api/manifest.json`), the domain keeps
  a class with the fields only, no `rules`, at the published path, and the application validator extends it and
  declares `rules` (e.g. `SearchBuyerOrdersRequestValidator` and `StoreSearchOrdersRequestValidator`).

## Joins

- Nested joins are listed by their full path: `{ path: 'purchases', populate: [{ path: 'vendor' }] }`
  needs `purchases` and `purchases.vendor`.
- Only `path` and `populate` are read from the client (no `select`, `match` or `model`).
- A path with spaces (`user customer`, several paths at once in Mongoose) never matches the list.

## `$regex`

- The value is always a literal search term: it is escaped before it reaches Mongo, so `a.b` matches
  `a.b` only. Escaping is idempotent, so a term the client already escaped keeps working.
- At most 100 characters; `$options` only `i`, `m` or `s`.
- No endpoint takes raw patterns today. If one ever needs them, it gets its own rule, not a global switch.
