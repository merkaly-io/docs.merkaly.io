Two domains, two uses:

- **`auth.merkaly.io`** (custom): what users and apps see. Frontends log in against it
  (`auth0.domain` in each `nuxt.config.ts`) and the api validates tokens against it
  (issuer `https://auth.merkaly.io/`, JWKS `https://auth.merkaly.io/.well-known/jwks.json`).
  New Universal Login page templates require a custom domain.
- **`merkaly.us.auth0.com`** (canonical): the **Management API** (`/api/v2/`, `/oauth/token`
  for M2M). Never call the Management API on the custom domain: the api fails to boot and
  login breaks.

## API

One custom API (resource server), `api.merkaly.io`:

| Setting | Value | Why |
| --- | --- | --- |
| Identifier (audience) | `https://api.merkaly.io` | every SPA requests it; the api checks it (`AUTH0_AUDIENCE`) |
| Signing algorithm | `RS256` | the api verifies with the public JWKS of `auth.merkaly.io` |
| Allow offline access | **on** | without it Auth0 issues no refresh tokens and every SPA session ends with the access token |
| Token lifetime (`token_lifetime`) | `86400` (24h) | non-browser flows |
| Token lifetime for web (`token_lifetime_for_web`) | `7200` (2h) | the access token SPAs get; renewed with the refresh token |
| Token dialect | `access_token` | |
| RBAC (`enforce_policies`) | off | roles are read from the `https://merka.ly/authorization` claim, not from permissions |
| Scopes | none | |
| Skip consent for first-party apps | on | |

System APIs (not configured by us): Auth0 Management API (`https://merkaly.us.auth0.com/api/v2/`)
and Auth0 My Account API (`https://merkaly.us.auth0.com/me/`).

## SPA apps

Common to every SPA: type `spa`, first party, OIDC conformant, `token_endpoint_auth_method: none`
(public client, no secret), ID token `RS256` with `lifetime_in_seconds: 36000` (10h),
cross-origin auth off, SSO on, application name `<surface>.merkaly.<tld>` (see
[Surface clients](#surface-clients)). Callbacks and origins list production (`*.merkaly.io`) and
local (`*.merkaly.test`) hosts in the same app; there is a single tenant for both.

The `@merkaly/nuxt` module logs in with `audience: https://api.merkaly.io`,
`scope: openid profile email offline_access`, `useRefreshTokens: true` and
`cacheLocation: localstorage`, with the callback at `/auth`. See its README for what the
module does with the session.

## Surface clients

Every frontend sends its Auth0 client id in the `x-merkaly-client` request header (added by
`@merkaly/nuxt`). The api lists the tenant applications at boot and uses their **application
name** both to identify the caller in its logs and to decide which routes each app may call, so
the name is a requirement, not a label: it must be `<surface>.merkaly.<tld>`.

| Application name | Surface | Routes it may call |
| --- | --- | --- |
| `admin.merkaly.io` | `admin` | `/admin/*`, `/auth/*` |
| `dashboard.merkaly.io` | `dashboard` | `/dashboard/*`, `/auth/*` |
| `store.merkaly.io` | `store` | `/store/*`, `/auth/*` |
| `www.merkaly.io` | `www` | `/www/*`, `/auth/*` |

There is no fixed list in the api: **every** application named `<x>.merkaly.<tld>` is a known
app with surface `x`, so it may call `/auth/*` and, if the api has one, `/<x>/*`. The account
linking client `auth.merkaly.io` and the M2M `api.merkaly.io` are known apps too: `auth` is the
shared `/auth/*` and the api has no `/api` routes, so they only reach `/auth/*`. Names that do not follow the pattern
are ignored. Dev tenants use the same names with their tld (`admin.merkaly.test`).

Renaming an app changes which routes accept it; restart the api afterwards, since it reads the
applications only at boot. The api needs `read:clients` for this (see [M2M apps](#m2m-apps)).
How the api uses it: [api clients](/tecnico/api/conventions/clients).

## Refresh tokens

What every Nuxt app relies on, in place since 2026-11-04 for admin, dashboard and www:

| Setting (Management API field) | Dashboard label | Value |
| --- | --- | --- |
| `refresh_token.rotation_type: rotating` | Refresh Token Rotation | on |
| `refresh_token.expiration_type: expiring` | Refresh Token Expiration | on |
| `refresh_token.idle_token_lifetime` | Idle Refresh Token Lifetime | `2592000` (30 days) |
| `refresh_token.token_lifetime` | Maximum Refresh Token Lifetime | `7776000` (90 days) |
| `refresh_token.infinite_idle_token_lifetime` / `infinite_token_lifetime` | Set Idle / Maximum Lifetime | `false` / `false` |
| `refresh_token.leeway` | Reuse Interval | `30` (seconds) |

Rules:

- Never non-rotating or non-expiring for a browser app.
- The API must keep **Allow Offline Access** on, and the app must request `offline_access`.
- A user who stays away more than 30 days, or is signed in for more than 90, logs in again.

**Reuse interval 30s (`refresh_token.leeway: 30`), set on admin, dashboard, www and store on
2026-11-05.** With rotation, each refresh token is single use; if two tabs (or a retried request)
refresh at the same time, the second one reuses an already rotated token, Auth0 treats it as a
replay, revokes the whole token family and the user is logged out. A 30 second reuse interval
tolerates that race without weakening rotation in practice. Keep it on any new browser app.

## Actions

Source in `src/actions/`, deployed with the opt-in `actions` target (see the
[README](https://github.com/merkaly-io/auth.merkaly.io/blob/master/README.md#actions)). Never edit them in the dashboard.

`post-login` bindings, in this order (`src/actions/bindings.json`):

1. **Add information to userinfo context** (`src/actions/add-information-to-userinfo-context`):
   sets `https://merka.ly/authorization` (roles) on access and id tokens. No secrets.
2. **Enforce surface access** (`src/actions/enforce-surface-access`): denies the dashboard
   client to users without an `MK_*` role. No secrets.
3. **Link accounts by verified email** (`src/actions/link-accounts-by-email`): when the
   login's email is verified and another user with the same verified email exists, links the
   current user into the oldest one (`POST /users/{primary}/identities`) and continues the
   session as it (`setPrimaryUser`). Only links when the current user is empty (no
   organizations, no `app_metadata.merkaly`); otherwise logs for manual resolution. Skips
   refresh token exchanges and non-interactive flows; fail-open on any error, so a
   returning store owner with a new login method keeps their store.
   Secret: `AUTH0_CLIENT_SECRET` (needs `read:users`, `update:users`, `read:organizations`).

All three run on Node 22, `post-login` v3, without npm dependencies. Secret values are set
only in Auth0 Dashboard > Actions > Library > the action > Secrets. No other triggers are bound.

**Self-service signup** (`src/actions/self-service-signup`) is **unbound, pending deletion**.
It rendered the onboarding Form to www logins without organization and posted
`signup.requested` to `https://webhooks.merkaly.io/auth0`, creating the organization without
CPF or birth date. Signup now lives in www `/create` (`POST /www/onboarding`, identity in
`app_metadata.merkaly.identity`). The Action still exists in the tenant (the deploy keeps it
updated, unbound) with secrets `AUTH0_WEBHOOK_SECRET` and `AUTH0_CLIENT_SECRET`, until the
cleanup that deletes it together with its Form and the `signup.requested` path.

## Event streams

Auth0 events (`user.*`, `organization.*`...) reach Merkaly through Event Streams, not Log
Streams (webhooks.merkaly.io no longer accepts log stream payloads). One stream, webhook
destination, created in Auth0 Dashboard > Event Streams or with `POST /api/v2/event-streams`:

| Setting | Value |
| --- | --- |
| Endpoint | `https://webhooks.merkaly.io/auth0` |
| Authorization | Bearer token, same value as `AUTH0_WEBHOOK_SECRET` |
| Subscriptions | 25 types: `connection.*`, `group.*`, `organization.*` (incl. `organization.connection.*`, `organization.group.role.*`, `organization.member.*`), `user.created`, `user.updated`, `user.deleted`. Only `organization.member.added`, `.deleted`, `.role.assigned`, `.role.deleted` are translated (team members cache in the api); the rest is acked with `200` and a warn line |

Deliveries and payloads are checked in the stream's delivery history (webhooks does not log
bodies). The stream is not deployed as code yet. Signup does not use it: www `/create`
calls the api directly (`POST /www/onboarding`). The `signup.requested` event came from the
unbound legacy Action, not from the stream. Payload, logs and answers: webhooks.merkaly.io README, section Auth0.

## New tenant checklist

In order:

1. **Tenant.** Create it in the US region. Set friendly name, picture, support email and
   URL, enabled locales (`en fr it pt-BR es`), default redirection URI and tenant logout URLs
   as in [Tenant and domains](#tenant-and-domains). Enable New Universal Login and identifier
   first; enable the WebAuthn platform and recovery code factors.
2. **Custom domain.** Add `auth.<domain>` with Auth0-managed certificates, create the CNAME,
   wait for `ready`, make it the default.
3. **M2M `auth.merkaly.io`.** Create it with the 10 scopes in [M2M apps](#m2m-apps); put its
   secret in this repo's GitHub secret `AUTH0_CLIENT_SECRET`; update `AUTH_CLIENT_ID` in
   `src/actions/_shared/clients.ts` and `AUTH0_CLIENT_ID` (plus `AUTH0_DOMAIN` if the tenant
   name changes) in `.github/workflows/deploy.yml` and your local `.env`.
4. **API.** Create `https://api.merkaly.io`: RS256, allow offline access on, token lifetime
   `86400`, for web `7200`, RBAC off.
5. **M2M `api.merkaly.io`.** Create it with the minimal scopes; set `AUTH0_CLIENT_SECRET` in

   JWKS URI); frontends `auth0.domain`.

10. **Connections.** Enable `default`, `google-oauth2` and `apple` (and `github` where listed)
    per app as in [Connections and organizations](#connections-and-organizations); configure
    the Google and Apple social apps with the tenant's callback.

## New app checklist

1. Create an application of type **Single Page Application**, named as in step 5.
2. Callbacks `https://<app>.merkaly.io/auth` and `https://<app>.merkaly.test/auth`; logout
   URLs, web origins and allowed origins with the same hosts (no path); initiate login URI
   `https://<app>.merkaly.io` (the root, never the `/auth` callback).
3. Refresh tokens: rotation on, expiration on, idle `2592000`, maximum `7776000`
   (reuse interval per [Refresh tokens](#refresh-tokens)).
4. Organizations: `require` with `post_login_prompt` if the app works inside a store,
   `deny` for staff tools, unset for public apps.
5. Name the app `<surface>.merkaly.<tld>` (see [Surface clients](#surface-clients)); renaming
   an app changes which api routes accept it, restart the api afterwards.
6. Enable the connections the app needs (`default`, `google-oauth2`, `apple`).
7. Staff only: add the client id to `src/actions/_shared/clients.ts` and to the
   `Enforce surface access` rule, then deploy the actions.
8. In the app's `nuxt.config.ts`: `auth0.client`, `auth0.domain: auth.merkaly.io`,
   `auth0.audience: https://api.merkaly.io`, `auth0.callbackUrl: /auth`.
9. Update this document.

## Known gaps

- **Single M2M (api.merkaly.io) for the api, the deploy and the Actions** (2026-11-05, while
  testing without users): its secret lives in Railway, GitHub and two Action secrets, and it can
  rewrite Actions. Split it again (a deploy-only M2M plus an Actions-only M2M) before external
  clients.

Observed on 2026-11-05, not changed. Fixed the same day: the Management API grants of the
store and dashboard SPAs were removed and the linking client lost the `account.merkaly.*` hosts.

- **`api.merkaly.io` M2M** is still enabled on the `default` and `github` connections (harmless
  with `client_credentials` only). Its scopes and grant types were trimmed on 2026-11-05; when the
  api starts calling a new Management endpoint, add only that scope here and in Auth0.
- **Store** still has the `password` and `password-realm` grants on a public SPA.
- **Account linking client** (`auth.merkaly.io` in Auth0) has non-rotating, non-expiring refresh
  tokens.
- **Implicit grant** is still enabled on every SPA; the SDK uses authorization code with PKCE.
- **Default audience** is the Management API; a token request without `audience` gets a
  Management API token. Every app sends `https://api.merkaly.io`, so it is not hit today.
- **www has no `default` connection**: signup from www is social only (Google, Apple).
- **Tenant session lifetimes** are not set (Auth0 defaults).
- **Require verified email to use the apps** (planned, not now). Database signups stay
  unverified until the user confirms the email, so `Link accounts by verified email` skips
  them; they link on the first login after verifying, while still empty. Until the apps
  require a verified email, an unverified user can create data (e.g. a store) and then need
  manual resolution.
- **Custom domain verification** reports `failed` (last checked 2026-08-20) although the
  domain is `ready` and serving; check the CNAME.

Not readable with the api M2M token (403): Forms, Flows, attack protection (breached
password, brute force, suspicious IP). Connection options come back empty. No email
provider is configured (404).
